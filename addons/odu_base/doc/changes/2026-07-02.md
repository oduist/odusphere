# 2026-07-02

The installation-policy governance was widened so the `mail` messaging/activity
framework (chatter, activities, mail templates) may be used by `odu_*` modules,
and the allow-list now expands by dependency closure so transitive framework
dependencies no longer have to be listed by hand.

## tech_spec.md

### Changed

- **Models & Fields** — `ALLOWED_FRAMEWORK_MODULES` now includes `mail` alongside
  `base` and `web`.

```diff
- `ALLOWED_FRAMEWORK_MODULES = frozenset({"base", "web"})`
+ `ALLOWED_FRAMEWORK_MODULES = frozenset({"base", "web", "mail"})`
```

- **Business Rules & State** — the installation policy's allowed set is now the
  framework roots **plus their full dependency closure**; only the roots are
  expanded, so an `odu_` module cannot pull in a business app through a dependency.
- **Methods & Actions** — `_odu_allowed_module_names` now returns the roots unioned
  with their dependency closure.

### Added

- **Methods & Actions** — new helper `_odu_dependency_closure(self, names) -> set[str]`:
  breadth-first walk of the `dependencies_id` graph that returns every transitive
  dependency name of the given roots (what makes allowing `mail` also allow `bus` /
  `base_setup`).

## admin_guide.md

### Changed

- **Allowing an extra framework module** — the built-in framework set is now
  `base`, `web`, `mail`; added a note that a directly-allowed module's own
  dependencies are allowed automatically (no need to list transitive deps), while
  business apps stay blocked.
